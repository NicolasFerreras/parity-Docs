# Parity — Sistema para estandarización, formateo y matcheo de órdenes de compra

<Tip>
Proyecto Integrador 1 — **Raz y Cía.** Stack `Go + PostgreSQL + React + TypeScript` · API HTTP · Docker. Datos sensibles: `lista_articulos.xlsx` nunca se usa en prod, solo fixtures en `testdata/`.
</Tip>

## Propósito

Parity automatiza el ciclo **Excel → validación → matcheo contra catálogo → revisión humana → persistencia** para órdenes de compra que hoy se procesan manualmente. Elimina re-tipeo, reduce errores de código/cantidad y deja trazabilidad `R → US → TC`.

## Alcance MVP

<Steps>
  <Step title="Upload & parsing Excel">
    Handler `cmd/server` → `internal/parser` (excelize, límite 10MB) → `internal/ordenes`
  </Step>
  <Step title="Validación">
    Cabecera + líneas, filas fantasma, encabezados variantes, decimales
  </Step>
  <Step title="Matching">
    `internal/matching/normalize.go` → `barcode.go` → `description.go` → scorer → estados `exact/ambiguous/failed`
  </Step>
  <Step title="Revisión & edición manual">
    `src/features/matching` — tabla con badges, modal edición
  </Step>
  <Step title="Persistencia">
    PostgreSQL `migrations/*` — `orders`, `order_lines`, `articles`
  </Step>
</Steps>

## Fuera de alcance (MVP)

<Warning>
No incluir sin `Problema → Requisito → Necesidad → Alternativas → Decisión → Tecnología` y Human Gate.
</Warning>

- Colas / async (RabbitMQ), microservicios, K8s, Redis/caching
- OCR foto borrosa WhatsApp (PP4b) — pedir reenvío
- Auth compleja / multi-tenant
- `lista_articulos.xlsx` real en prod — siempre fixture

| Capa | Stack | Patrón |

| DB | PostgreSQL 16 | migraciones versionadas |
| Frontend | React + TypeScript | `src/api/types.ts` contrato tipado |
| Infra | Docker Compose, GH Actions | `docker`/`ci-cd` |

## Principios no negociables

<Card title="Human Gate (§4)" icon="shield-check">
Ningún agente escribe/modifica, commitea, pushea, elimina, mueve Done, cambia MVP, instala dependencia o decide con ambigüedad sin confirmación vía `question`.
</Card>

<Card title="Modo Plan (§5)" icon="file-check">
Antes de construir/modificar/ejecutar cualquier cosa, plan breve: qué / qué NO / archivos / riesgos / reversibilidad → esperar `aprobado`. El agente puede **sugerir** modo plan si lo considera necesario, nunca decidir por el usuario.
</Card>

<Card title="Ramas y datos (§13-§14)" icon="git-branch">
Branch propia, nunca `main` directo. Tests contra DB fixture. `git pull --rebase origin main` antes de merge, serializar merge, nunca `--force`.
</Card>
